### The lesson worth carrying forward
**A mechanism's RED may only be a RED for its DEPLOYMENT FORM.** L123 and L124
are the identical C++ change. What differed: L123 forced one setting on every
case; L124 puts both behaviours in the pool and lets the proxy arbitrate. That
is worth 1.6–2.5 percentage points.

The screening test is cheap and the machine already exists (`l124_r3_scale.py`,
~20 min per flag): capture each pool profile's output under the flag ON and OFF,
compute the **per-case 2-way oracle**, then simulate any subset offline. If the
oracle is positive on both samples, the twin form is worth building.

⚠️ **No per-case classifier is involved** — that is what M56/M79 killed. The
proxy is oracle-perfect on heterogeneous candidates (M76/M77), so the twin only
has to be *available*, not *predicted*.

⚠️ **There is no second fish this size.** MIB was worth +1.2% because of a
structural in-set/held-out asymmetry (in-set V_mib = 0, held-out 74.9% of all
soft violations). Every other structural axis matches across the two corpora —
boundary 34.1% vs 33.0%, cluster members 28.8% vs 27.2%, MIB members 7.1% vs
6.4%, mixed clusters 53.8% vs 56.7%. Remaining candidates are ~+0.2%.

## 3. 🚨 Things that will silently mislead you

08-12's list still applies. These are new, and the first one nearly cost the
whole session's gain.

1. **The bundled Linux binary is a separate artefact from `constructive.cpp`.**
   `bin/constructive_linux` was a pre-L124 build with **zero** occurrences of
   `ICCAD_MIB_BUCKET`. The Linux grader resolves it **before** the compile chain
   (bundled-binary-first, M67-A/C), so it would have ignored the flag, the eight
   twins would have emitted exactly what their sources emit, and the entire gain
   would have evaporated — **with every Windows gate passing**, because Windows
   compiles from the .cpp. Caught only by diffing the tar's members against the
   working tree. **Any change to `constructive.cpp` requires rebuilding the
   bundled binary** (`g++ -O3 -std=c++17 -static-libstdc++ -static-libgcc`, no
   `-march`, from WSL) **and a `strings` check that the new knob is in it.**
2. **`l113_ship_gate.py` re-stages the package.** It rebuilt the tar from a
   modified `constructive.cpp` mid-session. **Re-verify the tar's contents after
   running any gate**, member by member, against the working tree.
3. **There are now THREE tiers gated at ≥40 cores** (tier-5, M80, L124), and each
   gate's `_ISOLATE` must pin the other two. Missing one does not weaken the
   gate quietly — it fails it, on a correct pool.
4. **`Gate B` and `gate0` in `m67_oos_probe` anchor on the 32-core
   `results_M74_default.json`.** Under `--force-cores 48` they report confident
   false FAILs on correct solves (gate0's case 99 read `1.2715188353111`, which
   is bit-identical to the 48c anchor). Not fixed — read them with this in mind.
5. **`target_positions=None` sinks every case to 10.0.** It carries the
   preplaced/fixed placements. A first cut of the R2 script passed None and
   measured 10.0 on all 100 cases. Same input-mismatch M75 recorded.
6. **Setting PATH for the compiler is right for gates and WRONG for probes.**
   Gates need it (m48 exercises the compile chain). Probes must not have it: the
   chain compiles into `_BIN`, which for a probe run is the **probe binary**, and
   silently overwrites it.
7. **`m67_oos_cache_c48.pkl` was contaminated** — its signature pinned
   `04e7c86bd4d6` (the L123 build), so its `cases` endpoint was solved with
   bucketing ON, not the shipped configuration. The A/B was still valid (both
   endpoints, same binary), but the label was wrong. The signature *does* pin the
   exe (12-char prefix) — what it does not pin is the Python-side shape-LP /
   route-A identity.
8. **`m77_oos_audit.pkl` is empty** (0 entries). Rebuilding it is ~16,800 solves.
9. **The probe runner's output filename must encode the SETTING.** An early
   revision hardcoded `mibon`, and a `--bucket 0` run silently overwrote 334 s of
   `--bucket 1` output.

**L125 / bounded beam: RED, and the reason generalises.** Full report

L124's measured +0.4697% — and it is still dead, because at 48 cores it cannot be

* a twin set's dRF is **the dRF of its slowest member** (the wall is the

* the pool's runtime distribution is **bimodal** — 14 of 51 profiles sit far below

* restricted to what can be paid for, the ceiling collapses to **+0.0956%**, and
  even a hypothetical **1.15×** beam (cheaper than any W=2 beam can be) only
  reaches +0.1398% free, or +0.2152% against a 0.30% RF budget ⇒ **negative NET**.

🔑 **The twin screen has a second precondition that was never written down: the ON
side must be TIME-NEUTRAL.** L124 shipped partly because MIB bucketing is a
construction-time decision that costs nothing. Anything slower can only be applied
to the quarter of the pool with wall headroom, and that quarter carried **12%** of
the beam's twin value. **Price the eligible-source set before building** —
`l125_beam_price.py afford` is ~45 min of serial timing and would have killed this
before a line of C++.

Also worth carrying: the A/B's parallel timing read the beam at 2.30×; measured
serially it is **2.06×**. B0's `m = W` assumption was right and the "correction"
was contention. Timing under load is not timing.

### Route 3 risk, stated in advance
`layout_score` has **no monotone relationship to final cost on partial layouts** —
that is exactly what killed the frame-level B&B (`guide.swap` runs
unconditionally and three nudges break bbox monotonicity). So the beam's
**pruning criterion is itself unreliable**; top-W need not retain the eventual
winner. Beam tolerates this better than B&B (it keeps W, not 1), but this is
where it will fail if it fails.
