## 3. 🚨 `origin + offset` does not abut, and it is in the shipped result (L131)

The evaluator builds a block's far edge as `x + w`. Floating-point addition is
not associative, so `(lx+ox)+w` and `lx+(ox+w)` differ by an ULP: a packing that
abuts exactly in exact arithmetic lands **±2.8e-14** off, and `unary_union`
either merges the group or splits it.

Case 66, same packing, relative offsets identical to 1e-6: v6 landed on
**+2.84e-14** (a GAP → two geometries → `grouping_violations = 1`), the
alternation on **−2.84e-14** (a hair of OVERLAP → merged → 0). Opposite verdicts
from the last bit.

**In the shipped 48c result: 2 of 16 grouping violations (12.5%) are this**, on
cases 69 (n=90) and 78 (n=99). Snapping them and re-running the OFFICIAL
evaluator:

    weighted total BEFORE   1.236791669773      <- the shipped 48c score, to every digit
    weighted total AFTER    1.235854685125
    worth                   +0.0758%
    infeasible before/after 0 / 0

Two facts make this cheaper and safer than it sounds:

* `check_overlap` (`iccad2026_evaluate.py:223`) ignores overlaps below **1e-6**
  — "touching edges OK". Gaps are 1e-14 and a snap moves a block ≤1e-9, so it
  **cannot** manufacture an overlap violation. Five orders of magnitude of margin.
* `op_wrapper.py` is generated by `make_submission.build_op_wrapper_text()`, so
  the fix is a positions post-process in one reviewable Python function. **No C++
  rebuild, binary md5 unchanged.**

Two sites in `constructive_l124.cpp` have the defect: the item emit at `:1039`
and `:1069` (`x + it.offs[k]`, offs accumulated at `:450`), and
`final_group_boundary_nudge` at `:1146` (rigid translate). The file's own header
already knew the shape (`:28`, "FP translation breaks exact abutments") — as a
reason to reject a different feature, not as a bug in the paths that shipped.

## 3b. 🚨 The biggest known quality item: MARGIN costs up to +0.3566% (L135)

Looking for more of L131's family found something larger and harder. First, the
ULP family is **closed and had exactly one member** — boundary checks with
`eps = 1e-6` and MIB compares `round(dim, 4)`, so only `unary_union` was exposed.

The new one is a real violation. `constructive_l124.cpp:51` sets `MARGIN = 1e-4`
and the frame is sized `max(w, pre_w + MARGIN)` (`:683`, `:1972`) — deliberately
1e-4 larger than the preplaced extent it must contain. Blocks packed against the
frame define the bbox at `X.0001`; a **preplaced** block sitting at the true
`X.0` misses by exactly MARGIN and scores a boundary violation.

    case 54 blk 3   right edge 141.0   bbox xmax 141.0001
    case  7 blk 4   top   edge 100.0   bbox ymax 100.0001

🔑 **Unsatisfiable by construction**: the block's position is HARD so it cannot
move to the bbox, and the bbox is 1e-4 beyond it. All 10 are preplaced, which is
why every boundary repair the C++ already has skips them.

**Prize: +0.3566%** (10 violations, priced with the real `nsoft` and the
multiplicative cost). That is 4.7× L131's fix and above the 0.30% OOS ship bar —
but it is an **upper bound**, since any real fix changes the frame and the frame
drives the packing.

**Three post-process attempts all fail** (L135 §4): moving the block is
infeasible (position is HARD); snapping anything near an edge moved 423 blocks,
removed 0 violations and cost **−1.1401%** by breaking cluster abutments with
ULP-scale nudges (§3.1 for the fourth time); and pulling the bbox in creates
exactly-1e-4 overlaps because the packing is tightly abutted.

## 5. 🚨 New silent-failure notes

08-15 §3 still applies. These are this session's, and three cost real time.

1. **A per-case normaliser that defaults to 1.0 gives a plausible number, 3×
   out.** `l131_abut_audit.py` first priced its own finding as
   `cost*exp(BETA*dV_rel)`, reading `N_soft` from the results json — **an official
   results json has no `nsoft` field** (that key is an L129 addition), the
   fallback was 1.0, and `vr - spurious/N_soft` removed EVERY violation on those
   cases instead of one. Reported **+0.2196%** against the official **+0.0758%**.
   The tool now counts and refuses to price; `l131_snap_verify.py` prices by
   re-running the real evaluator.
2. **The OOS audit cache can be destroyed by the next command.** After a
   successful 8400-combo build, running `score` left `m77_oos_audit.pkl` at
   33,280 bytes with `data` empty and `index` kept — `_cload()`'s sig-mismatch
   branch (`m77_oos_probe.py:183`). Symptom: `"no cached profile at cores=48 ->
   run build for this sample first"`, indistinguishable from never having built.
   **Two hypotheses tested and both false**: SIG is stable across processes and
   PATH (`86b1f6ba`, `_exe_md5 dc47a572`, same with and without msys), and
   `_cload()` does run before mode dispatch. **Root cause NOT established.**
   Mitigation: run build and score in ONE command chain, and `cp` the pkl to
   `.bak` immediately after the build. Done that way, sig matched before and
   after and the cache survived both scores.
3. **`exp(n/12)` means the first 30 cases are 3.7% of the score and n≥80 is
   96.3%.** A 30-case sample said −9.6% where the graded mix said +0.003%.
   `--minn` / `--maxn` were added to `l129_global_placer.py` for this; iterating
   on `--limit 30` measures the part nobody is graded on.
4. **Solo cost and the portfolio gate are close to anti-correlated here.** Best
   solo (1.6260) gates at +0.003%; worst solo (1.8318) gates at +0.045%. M77's
   opening argument, in the direction nobody expected — and I used solo cost to
   steer for several rounds before noticing.
5. **`--dt 0` is an ASSUMPTION that reads like a measurement.** Passing it makes
   the tool report `dRF@48c = +0.000%, 0 cases set a new wall`, which is a
   tautology; the real numbers are +38.3% and +31.7%. Both probes print a warning
   about precisely this and it was overridden for an entire session. Worse, on
   this machine the OOS probe **crashes while printing that warning**
   (`UnicodeEncodeError: cp950` on `⚠`, `m77_oos_probe.py:766`) — so the
   honest path fails loudly and the optimistic path succeeds quietly. Run it with
   `PYTHONIOENCODING=utf-8`.
