## 3. L138 — IN PROGRESS. An upper bound, not a result.

The question is cost, not quality. L137's clean timing established that on every
heavy case the binding term of M67-E's wall model is **`max_k dt_k`**, not
`sum_k dt_k / cores` (e.g. case 99: max 1.542s vs sum/48 0.883s). So the per-case
wall is ONE profile's runtime.

`l138_wall_setter.py` re-asks M41/M42's question of today's pool, using the REAL
selector (`(area/Â + 1.4·hpwl/hmin)·exp(2·vrel)`, `oc:2122`) and **re-selecting**
after each drop rather than subtracting — `hmin` is the pool minimum, so removing
a profile re-scales the hpwl term for every survivor.

Measured, 13 cases n≥108, 48c pool:

* the max-setter is **never** the winner (0/13), and dropping it never moves the
  winner (13/13) — but it only buys **1.85%**, because the max-setter is a
  different profile on every case and the second-slowest simply takes over. The
  distribution is flat; M41/M42 already removed the outliers.
* dropping the **K=10 slowest per case**: weighted wall **1.3309s → 1.1585s,
  −12.95%**, winner preserved on 12/13 (case 94 breaks at K=4).

🚨 **This is an UPPER BOUND and is not deployable as measured.** Three reasons,
all of which must be closed before anyone believes the 12.95%:

1. **The drop set is chosen per case from that case's own timings.** A real
   system must fix one profile set in advance. The deployable question is which
   profiles are slow AND never win **across** cases — a different and harder
   question than the one answered.
2. **In-set only.** cap2 in L137 won in-set on BOTH axes and came back −0.0575%
   OOS. Pool pruning is historically worse than that: M67-D measured the adaptive
   cuts' OOS quality tax at **+2.825%** against an in-set +0.106%, a 27× gap. The
   prior here is bad, not good.
3. **Case 94 breaks at K=4**, so the threshold is already fragile at 13 cases.

**Next step**, if continued: count, across cases, which profile indices are
consistently in the slow tail and never selected; form ONE fixed drop set; measure
it in-set; then OOS on the 240. Do not quote 12.95% as a gain.

## 4. 🚨 Silent-failure notes (this session's four)

08-16 §5's list still applies. These are new, and every one produced numbers that
looked entirely reasonable.

1. **`--dt 0` is an ASSUMPTION that reads like a measurement.** It tells the probe
   the candidate is free, so `dRF@48c = +0.000%` is a tautology. Real values were
   +38.3% / +31.7%.
2. **A tool's own hygiene can delete your experiment.** `m77_oos_probe` strips
   every `ICCAD_*` at import — correct for its job — and `l137_oos_ab.py` imported
   it before reading the knob, producing two **byte-identical** 240-case arms: a
   clean, plausible, completely empty A/B. Capture knobs BEFORE the import and
   print requested-vs-actual.
3. **`verify` does not re-stage.** The first `build_submission.L136FIX/` I saved
   carried the OLD Linux binary because the last `stage` predated the swap. Scores
   were unaffected (Windows never reads the bundle) — only the artefact was wrong.
   Stage after every input change and check md5s in the STAGED tree.
4. **The gate's wall-clock cannot measure a few percent.** Re-running identical
   arms moved the baseline's own wall 4.225s → 5.051s, a **19.6% spread**. Costs
   are bit-identical across repeats (the placer is deterministic), so quality is
   safe; timing is not. Use per-profile min-of-N through
   `max(max dt, sum dt/cores)`. I stated "faster AND better" off the noisy number
   and had to withdraw it.

🔑 The pattern in all four: **the tool ran, the numbers were plausible, and the
thing being measured was not the thing intended.** What caught each was an
internal consistency check, never the result looking wrong — e.g. cap6 (6 passes)
cannot be slower than no-cap (12).

🔑 And the standing rule that was mis-applied: **L125's "price it before building"
means price what the mechanism costs when DEPLOYED, not how long its code runs.**
Pricing only the new code missed the hint's effect on the consumer by 3×.
